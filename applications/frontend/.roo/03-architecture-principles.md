# フロントエンドアーキテクチャ設計原則

## はじめに

本ドキュメントは、Feature-Sliced Design (FSD) をベースにした React フロントエンドアーキテクチャの設計思想を解説します。コード例は含まず、プロジェクト固有の要件に左右されない普遍的な原則を記述しています。

---

## 基本思想

### アーキテクチャの目的

1. **変更容易性**: 機能追加や修正が既存コードに与える影響を最小化する
2. **理解容易性**: 新規参加者が構造を素早く理解できる
3. **スケーラビリティ**: プロジェクトの成長に耐えうる構造
4. **テスタビリティ**: 各部分を独立してテストできる
5. **再利用性**: コードの重複を避け、共通部分を効率的に管理する

### 核となる原則

**「関心の分離」と「単一責任の原則」**

システムを機能的に独立した層に分割し、各層が明確な責務を持つことで、複雑性を管理します。

---

## レイヤー構造

### 5層アーキテクチャ

```
src/
├── app/           # Layer 5: アプリケーション
├── pages/         # Layer 4: ページ
├── features/      # Layer 3: 機能
├── entities/      # Layer 2: エンティティ
└── shared/        # Layer 1: 共有
```

### 依存関係の方向性

**上位レイヤーは下位レイヤーに依存できるが、下位レイヤーは上位レイヤーに依存してはならない**

```
app ──→ pages ──→ features ──→ entities ──→ shared
```

この単方向の依存関係により、循環参照を防ぎ、システムの理解と保守を容易にします。

---

## 各レイヤーの責務と思想

### Layer 1: Shared（共有層）

**思想**: プロジェクト全体で再利用可能な、ビジネスロジックを含まない純粋な技術的基盤

**責務**:
- UI コンポーネントライブラリ（ボタン、入力欄など）
- HTTP クライアント、API 通信の抽象化
- ユーティリティ関数（日付フォーマット、文字列操作など）
- 型定義の基礎（ID 型、共通インターフェースなど）
- 設定管理（環境変数、定数）

**特徴**:
- 他のレイヤーに一切依存しない
- ビジネスドメインの知識を持たない
- プロジェクト間で移植可能

**判断基準**: 「この機能は他のプロジェクトでもそのまま使えるか？」

---

### Layer 2: Entities（エンティティ層）

**思想**: ビジネスドメインの核となるデータモデルを定義し、外部世界との境界を管理

**責務**:
- ドメインモデルの型定義（チャット、ユーザー、商品など）
- API レスポンスからドメインモデルへの変換（マッパー）
- ドメイン固有の純粋な変換・計算ロジック
- エンティティ間の関係性の定義

**特徴**:
- UI やユーザーインタラクションを含まない
- 状態管理ライブラリに依存しない
- ビジネスルールは含むが、アプリケーションロジックは含まない
- 不変性を重視（データの変更は新しいオブジェクトを返す）

**判断基準**: 「このデータ構造はアプリケーションの中核となるビジネス概念か？」

**分離の理由**:
ビジネスドメインの変更（API の変更など）が上位レイヤーに影響を与えないよう、境界を明確にします。

---

### Layer 3: Features（機能層）

**思想**: ユーザーが実行できる具体的な機能単位でコードを組織化し、ビジネス価値を提供

**責務**:
- 状態管理（ローカル状態、サーバー状態、UI 状態）
- ユーザーアクションの処理（クリック、入力、送信など）
- API 呼び出しとデータフェッチ
- ビジネスロジックの実装
- 機能固有の UI コンポーネント

**特徴**:
- 機能ごとにフォルダを分割（例: チャット管理、フラッシュカード生成）
- 各機能は独立しており、他の機能に直接依存しない
- 機能横断的な通信は共有状態や pub/sub パターンで実現

**内部構造**:
- `model/`: 状態定義、ビジネスロジック
- `ui/`: 機能固有の UI コンポーネント

**判断基準**: 「これはユーザーが実行できる1つの機能として説明できるか？」

**設計哲学**:
機能を「垂直スライス」として扱うことで、関連するコードを近くに配置し、変更の影響範囲を限定します。

---

### Layer 4: Pages（ページ層）

**思想**: ルーティングとビジネス要件の橋渡し。機能を組み合わせて完全な画面体験を提供

**責務**:
- URL ルートと画面の対応づけ
- 複数の機能を組み合わせたページ構成
- ページ固有のローカル状態管理（フォーム入力など）
- ページレベルのレイアウト調整

**特徴**:
- 1 ページ = 1 ルート = 1 コンポーネント
- ビジネスロジックは含めず、機能レイヤーに委譲
- プレゼンテーション層として機能
- SEO、アナリティクス、ページタイトルなどページ固有の設定

**判断基準**: 「このコンポーネントは URL に対応する画面全体を表現しているか？」

**分離の理由**:
ルーティングの変更（URL 構造の変更）が機能レイヤーに影響を与えないようにします。

---

### Layer 5: App（アプリケーション層）

**思想**: アプリケーション全体を起動し、グローバルな設定と依存関係を初期化

**責務**:
- ルートレベルのルーティング定義
- グローバルプロバイダーの設定（状態管理、React Query など）
- 認証ガードやグローバルレイアウト
- アプリケーション全体に影響する副作用の初期化
- グローバルなエラーハンドリング

**特徴**:
- アプリケーションのエントリーポイント
- すべてのレイヤーに依存可能
- ビジネスロジックは含まない

**判断基準**: 「これはアプリケーション全体の起動に必要な設定か？」

---

## 状態管理の思想

### 状態の分類

#### 1. サーバー状態
- **特徴**: サーバーから取得し、サーバーと同期が必要
- **配置**: Features レイヤーの `model/` 内
- **管理方法**: Query ライブラリ（React Query / SWR など）

#### 2. クライアント状態
- **特徴**: クライアント側でのみ存在し、サーバーと無関係
- **分類**:
  - **グローバル状態**: 複数の画面で共有（例: ユーザー認証状態）
  - **ローカル状態**: 単一コンポーネント内（例: モーダルの開閉状態）

#### 3. UI 状態
- **特徴**: 純粋に UI の見た目に関する状態
- **例**: サイドバーの開閉、選択中のタブ、ローディング表示

### 状態管理の原則

1. **最小の状態**: 派生可能な値は状態として持たない
2. **単一の情報源**: 同じデータを複数箇所で管理しない
3. **状態の正規化**: 重複を避け、参照で管理
4. **適切なスコープ**: 必要な範囲でのみ状態を共有

---

## ルーティング統合

### ルーティングの階層

#### トップレベル（App 層）
- 認証フロー（ログイン、コールバック）
- アプリケーション全体のレイアウト

#### アプリケーションレベル（App 層）
- 主要な画面遷移
- 共通レイアウト（サイドバー、ヘッダー）

#### ページレベル（Pages 層）
- 個別の画面とその内部ナビゲーション
- ネストされたルート（詳細画面、編集画面など）

### 原則

- **URL は UI の状態を表現する**: 重要な状態は URL に反映
- **Deep Linking**: どの URL からでもアクセス可能に
- **プログラマティックナビゲーション**: ビジネスロジックから画面遷移

---

## 命名とファイル構造

### フォルダ命名

**kebab-case を使用**: `chat-management`, `user-profile`

**理由**:
- URL セーフ
- 大文字小文字を区別しないファイルシステムでも一貫性がある

### ファイル命名

- **コンポーネント**: PascalCase (`ChatMessage.tsx`)
- **ロジック・状態**: kebab-case (`atoms.ts`, `use-chat.ts`)
- **型定義**: kebab-case (`types.ts`)

### ディレクトリ構造の一貫性

各機能フォルダ内の構造を統一：
- `index.ts`: 公開 API の定義（バレルエクスポート）
- `model/`: ビジネスロジックと状態
- `ui/`: UI コンポーネント

---

## 公開 API の管理（バレルエクスポート）

### 思想

各レイヤー・機能は `index.ts` を通じて明示的に公開する API を定義します。

### 利点

1. **カプセル化**: 内部実装の詳細を隠蔽
2. **インポートの簡潔性**: 深いパス指定が不要
3. **リファクタリング容易性**: 内部構造の変更が外部に影響しない
4. **依存関係の可視化**: 何が公開されているか明確

### 原則

- 必要最小限のみを公開
- 内部実装の詳細は公開しない
- 型定義も公開 API の一部として扱う

---

## データフローの原則

### 単方向データフロー

```
User Action → Write Atom → Mutation → API
                                      ↓
                                   Server
                                      ↓
                              API Response
                                      ↓
                                Query Atom
                                      ↓
                               Derived Atom
                                      ↓
                              UI Component
```

### 原則

1. **データは上から下へ流れる**: Props を通じて子に渡す
2. **イベントは下から上へ流れる**: コールバックを通じて親に通知
3. **状態の変更は明示的**: 副作用を伴う操作は明確に分離
4. **派生データは動的に計算**: キャッシュではなく計算で導出

---

## エラーハンドリング戦略

### 階層的エラーハンドリング

#### 1. API レイヤー（Shared）
- HTTP エラーの検出と正規化
- ネットワークエラーのハンドリング
- 標準化されたエラーオブジェクトの生成

#### 2. 機能レイヤー（Features）
- ビジネスロジックエラーの処理
- エラー状態の管理
- リトライロジック

#### 3. UI レイヤー（Pages/Features UI）
- ユーザーへのエラー表示
- フォールバック UI
- エラーからの回復手段の提供

### 原則

- **早期検出**: エラーは発生箇所で即座に検出
- **適切な粒度**: エラーハンドリングを適切なレベルで行う
- **ユーザー視点**: 技術的詳細ではなく、ユーザーが取るべき行動を示す

---

## パフォーマンス考慮事項

### 状態の最適化

1. **状態の分割**: 大きな状態オブジェクトを避け、関心事ごとに分割
2. **派生状態の活用**: 重複した状態を持たず、必要に応じて計算
3. **メモ化**: 高コストな計算は適切にメモ化

### コンポーネント最適化

1. **コンポーネント分割**: 再レンダリング範囲を最小化
2. **遅延ロード**: 重いコンポーネントは必要になるまで読み込まない
3. **仮想化**: 大量のリストは仮想スクロールを使用

### データフェッチ最適化

1. **キャッシング**: 適切なキャッシュ戦略
2. **並列フェッチ**: 独立したデータは並列で取得
3. **楽観的更新**: ユーザー体験を優先し、バックグラウンドで同期

---

## テスタビリティ

### テストの階層

#### ユニットテスト
- **対象**: Entities の変換関数、Shared のユーティリティ
- **特徴**: 依存がなく、純粋関数をテスト

#### 統合テスト
- **対象**: Features の状態管理とビジネスロジック
- **特徴**: 状態の変更と副作用をテスト

#### E2E テスト
- **対象**: Pages 層のユーザーフロー
- **特徴**: 実際のユーザー操作をシミュレート

### テスタビリティを高める設計

1. **依存性の注入**: 外部依存を抽象化し、テスト時にモック可能に
2. **純粋関数の優先**: 副作用を含まない関数は簡単にテスト可能
3. **明示的な状態管理**: 状態の変更を予測可能に

---

## スケーラビリティ

### 機能の追加

新機能追加時の影響範囲：
1. Entities 層に新しいドメインモデルを追加（他に影響なし）
2. Features 層に新機能を追加（他の機能に影響なし）
3. Pages 層に新ページを追加（ルーティングのみ影響）

### リファクタリング

レイヤー内のリファクタリングは他レイヤーに影響しない：
- Features の内部実装変更は公開 API を維持すれば Pages に影響なし
- Entities のマッパー変更は型が同じなら Features に影響なし

### チーム開発

- 機能ごとに独立した開発が可能
- 明確な責務分担によりコンフリクトが減少
- 新規メンバーも構造を理解しやすい

---

## まとめ

### この設計が解決する問題

1. **複雑性の管理**: 明確な階層により、システムを理解しやすくする
2. **変更の影響範囲**: レイヤー分離により、変更が波及しにくい
3. **コードの重複**: 適切な抽象化により、重複を避ける
4. **テストの困難さ**: 依存性の方向が明確で、テストが容易
5. **スケールの問題**: 機能追加が既存コードに影響を与えにくい

### 設計原則の核心

**「関心の分離」を徹底することで、システムの各部分が独立性を保ち、全体として柔軟で保守しやすいアーキテクチャを実現する。**

この原則に従うことで、プロジェクトの規模や技術スタックに関わらず、一貫性のある保守可能なコードベースを構築できます。
